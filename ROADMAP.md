# Roadmap

What comes after the first release. Items are roughly in priority order within each section; none has a date yet. Comment on or open an issue if one matters to you.

## Next

- **Horizontal scaling and Kubernetes (first priority).** One nbsandboxd host caps capacity at what a single node holds (a 16 GB node fits about 5–6 runs at the default 2 GiB), so production use needs more nodes. Decided so far:
  - **One design, two deployments.** The same binary runs as `--role=all` (standalone, Docker Compose, development) or as separate `api` and `worker` replicas. Only the `Backend` differs: Docker containers through the socket proxy, or Pods through the Kubernetes API (no Docker daemon in a cluster; no privileged pods or node sockets). Both must pass `internal/isolation/backendtest`.
  - **API replicas** serve the API, UI and streams and cannot start containers. **Worker replicas** pull runs from the queue, start and supervise sandboxes (logs, limits, cancel, timeout) and hold the only permission to create them.
  - **Postgres in every mode**, replacing SQLite: queue with leases and heartbeats (expired lease → `interrupted`), the space write lock with fencing tokens, events with commit-ordered IDs so SSE resuming loses nothing, cancel requests, and `LISTEN/NOTIFY` with a polling fallback.
  - **Stateless nodes:** Postgres for the database, object storage for file contents; local disk only as throwaway scratch (a worker's run folder, caches). Losing a node costs only its active runs, which end as `interrupted`.
  - **Content-addressed storage:** each file's bytes are stored once under their hash; the file index (path, size, hash, modified time) lives in Postgres. Renames, moves and folder deletes are index updates in one transaction; a file's version is its hash; publishing a function copies index rows, not bytes; quota and listings come from Postgres. A cleanup job removes contents nothing points to.
  - **Runs:** the worker downloads the space into its run folder, mounts it, and afterwards uploads changed files and updates the index in one transaction that checks each file's version and the run's fencing token (a stale worker can't write back; on a conflict both copies are kept). Files a writing run changes appear when it ends; live logs and status are unaffected. Outputs and artifacts are uploaded when the run ends.
  - **Storage adapters** behind one small interface (put, get, head, and delete and list for cleanup only; no conditional writes or renames needed, since objects are immutable): **S3** (RustFS, Ceph, SeaweedFS, AWS S3, Cloudflare R2), **Azure Blob** native (Workload Identity on AKS, no storage keys; Azure has no S3 API, and an S3 gateway in front of it would add a hop and bring back keys). **Every mode uses object storage, standalone and development included** (one code path to test): Docker Compose in the repo adds Postgres and an S3-compatible store (RustFS by default), and `make ui-preview` starts just those two. Unit tests use an in-memory fake that passes the same test suite. Both adapters pass one shared test suite, run against RustFS and Azurite (the Azure Storage emulator). Written directly on the vendors' Go SDKs; Go CDK (`gocloud.dev/blob`) is the fallback if speed matters more than control.
  - **Kubernetes isolation:** standard `NetworkPolicy` only (deny-all for run Pods), plus a startup and periodic probe Pod that must fail to reach anything; if it succeeds, workers refuse to run notebooks. Hardened Pods (non-root, read-only root, no capabilities, seccomp, no service-account token). A sandbox runtime is optional through `runtime_class` (Kata on AKS Pod Sandboxing, Kata or gVisor on premises). The runner also writes its log to a file so the kubelet's log rotation can't truncate it.
  - **Shipped with the backend:** a Helm chart and Terraform examples (AKS with Workload Identity, Azure storage and Postgres; and any cluster with existing Postgres and S3-compatible storage), so a deployment starts from something tested.
  - **Network plugins (decided 2026-11-08):** any plugin that enforces NetworkPolicy; tested locally with Cilium and Calico, and kindnet (no enforcement) is refused by the probe. **Still to decide:** cluster versions supported, and a "check this cluster" command so the isolation report can be run inside each target cluster.
  - **Status (2026-11-07):** (1)–(5) done: the Kubernetes backend with its network probe, Helm chart and Terraform examples (docs/kubernetes.md). Postgres store in every mode; space files, run outputs and published versions in object storage, with the indexes in Postgres; roles `all | api | worker` with leases, fencing tokens, `LISTEN/NOTIFY`, cross-node cancel and live logs (docs/scaling.md); `make test-cluster` runs the integration suite through two API processes and two workers. Left: (5) the Kubernetes backend and network probe; (6) failure tests beyond a worker crash (Postgres restart mid-run), and a soak on the cluster stack.
  - **Order:** (1) split the run manager into submit and execute sides behind queue, wake-up and cancel interfaces, in one process, with no change in behaviour (done 2026-11-07; the one-writer-per-space rule was already enforced by the database); (2) Postgres store; (3) roles and leases; (4) the storage interface and its S3 and Azure adapters, the file index in Postgres, copying in and out of runs, and the cleanup job; (5) Kubernetes backend and network probe; (6) cluster tests, including killing workers and restarting Postgres mid-run.
- **Authentication with an external identity provider (second priority, needed for production).** nbsandbox becomes an OAuth 2.0 resource server and keeps no user table. Decided so far:
  - **Standard OIDC, no vendor lock-in:** the issuer's discovery document and published signing keys (JWKS), JWT access tokens (RFC 9068), claim names in config. Works with Entra ID, Keycloak, Okta, Auth0 and others; Entra ID and Keycloak are the first two tested.
  - **Checking a token:** signature with RS256 or ES256 only (never `none` or HMAC), exact issuer and audience (nbsandbox's own), `exp` and `nbf` with at most 60 s leeway, a maximum lifetime, keys cached and refreshed on an unknown key ID with a rate limit. Tokens are never logged. Short-lived access tokens (5–15 min); token introspection (RFC 7662) later, for instant revocation.
  - **Who:** the caller ID is the issuer plus a stable, never-reused subject (Entra: `tid` + `oid`; others: `sub`; never email or `upn`), stored as e.g. `entra:<tid>:<oid>`. A space's owner is that ID. `users.yaml` stays for development and standalone use, as `basic:<name>` IDs.
  - **On behalf of users:** client backends hold their users' tokens. A token issued for the backend is refused (wrong audience); the backend exchanges it for an nbsandbox token (Entra's On-Behalf-Of flow, RFC 8693 token exchange elsewhere), so nbsandbox sees the end user, and records the calling app (`azp`) on runs.
  - **What:** scopes or app roles (`scp` and `roles`) limit what a token may do: `nbsandbox.read`, `nbsandbox.files.write`, `nbsandbox.runs`, `nbsandbox.functions.invoke`, `nbsandbox.functions.publish`, `nbsandbox.admin`. Each route declares the scope it needs in the route table, and the generated authorization test covers too little scope, the wrong owner and the wrong space.
  - **Without user records:** a default quota and a cap on spaces per ID, overrides by ID in config; admin endpoints to list spaces by owner ID and change or remove the owner (for users removed from the identity provider, or an issuer change).
  - **Status (2026-11-07):** built and unit-tested: token checking, caller IDs as space owners, scopes per route (in the OpenAPI spec, with a generated test), settings, and the guide (docs/auth.md). Then per-ID quotas and space cap, admin endpoints for owners (scope `nbsandbox.admin`) and the calling app on runs. Still to do: testing against real Entra ID and Keycloak.
  - **Later:** grants keyed by ID (`space, principal, role`) for sharing a space; a web UI login (authorization code with PKCE, a server-side session cookie, since a browser's `EventSource` can't send a bearer token).
- **v0.2: Notebook functions.** Publish a notebook as a versioned function that other services call with JSON and get JSON back: nested parameters, a returned output (or an error object with the reasons), optional input and output schemas, live status over Server-Sent Events, and long-polling. Also file management in the API (folders, rename, move, folder delete) and a file-write API with conflict detection.
- **v0.3: Editor in the web UI.** Syntax-highlighted notebooks and files, cell-by-cell editing, a syntax check, file versions with conflict handling, uploads and file management, publishing from the UI.
- **v0.4: gVisor (`runsc`) as a second runtime**, with the isolation report showing both runtimes side by side and the trade-offs measured.
  - **Status (2026-11-08):** done. On Docker, `make report-linux` runs the suite on Linux with Docker Engine with `runc` and `runsc` (docs/isolation-report-linux.md); on Kubernetes, `make report-k8s K8S_RUNTIME_CLASS=gvisor` runs it under a gVisor RuntimeClass beside the default runtime (docs/isolation-report-kubernetes.md). Costs and the differences handled are in docs/gvisor.md. Later: the Linux reference report on a VM with 4 GB and the default 2 GiB per run.

## Later

| Item | What it adds | Where it lands |
|---|---|---|
| Fast starts (≤ 1 s) | Cut the 3–5 s before a run's first cell while keeping a fresh container per run: skip work at start (render HTML after the result, lighter imports, run nbclient directly instead of papermill), keep a small pool of **single-use pre-started containers** per published function version (created and kernel started ahead of time, used once, then removed), and later restore a booted kernel from a snapshot (gVisor checkpoint/restore, Firecracker snapshots) | runner image, isolation, runs |
| Deeper lint in the editor | ruff (as WebAssembly, in the browser): undefined names, unused imports, common mistakes across all cells | web UI |
| Completion through variables | `df.` after `df = pd.read_csv(...)`: follow return annotations in the completion index (built 2026-11-08: modules, aliases and names across cells), or the kernel's own completion in interactive mode | runner image, web UI |
| Audit log | Who uploaded, ran, downloaded or deleted what, and when | store, runs, observability |
| Admin operations | List and stop any run; drain mode before maintenance | runs, API |
| Resource tiers | e.g. small and large runs, chosen from a configured list | isolation, runs |
| Scheduled runs | Run a notebook on a schedule with fixed parameters | runs |
| Filesystem quotas | Quotas enforced by the filesystem, not just checked | host setup, spaces |
| Network access to registered endpoints | Runs have no network today. When notebooks need external APIs: the space owner registers HTTPS endpoints (within a list the operator allows); runs with endpoints join an internal network whose only exit is an egress proxy that permits just those hosts; private addresses (host, other containers, cloud metadata) are always refused; no DNS inside the container; every attempt is logged and shown with the run; isolation tests prove unregistered hosts and bypasses fail. Comes with **space secrets** (encrypted API keys injected only into runs, never logged or returned) | host setup, isolation, runs, API, web UI |
| Other notebook languages | R first, then Julia if asked for. One runner image per language, chosen from the notebook's kernel against an allow-list (smaller and patched separately, rather than one image with every language): the language's kernel, parameter injection (papermill supports R and Julia), a `nbsandbox.output()` equivalent writing the same status file, its package list for the missing-import check, and editor highlighting. Until then, non-Python notebooks are refused | runner images, runs, web UI |
| Bring your own image | A space or function names its own image (any language or package set), pinned by digest from an allowed registry, with the runner contract installed. Only after gVisor: a foreign image must not get `runc`'s level of trust | runner images, isolation, runs |
| Custom packages per space | A space's requirements built into a derived, cached image (today's dependency check becomes the input) | runner image, runs |
| Shared spaces | Members with read or read-write roles | runs, API |
| Interactive mode | Run cells live from the editor, without JupyterHub: nbsandboxd starts a long-lived **session** container from the runner image (same limits and mounts as a run, still no network) with a kernel server listening on a Unix socket in the session's folder, and proxies the Jupyter kernel protocol over a WebSocket. A session that can write holds the space's write lock like a writing run; read-only sessions run beside others. Idle timeout, maximum length, and a limit on open sessions. The kernel also answers completion and inspection with live values (`df.` lists the columns). Needs Authentication first | isolation, runs, API, web UI, runner image |
| Firecracker backend | Same `Backend` interface; must pass `internal/isolation/backendtest` | isolation |

## Won't do

| Item | Why not |
|---|---|
| Completion webhooks | The status streams (`GET .../runs/{id}/events` and `GET .../events`) and long-polling (`?wait=`) already tell a caller when a run finishes, without nbsandbox having to call out to other systems. Webhooks would also need outbound network access from nbsandboxd, request signing, retries and a delivery log. |
